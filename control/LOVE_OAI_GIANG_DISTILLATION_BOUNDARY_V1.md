# LOVE → PARADISE Distillation Boundary V1

## Purpose
Carry the verified/high-value LOVE architecture into the new PARADISE/OAI-GIANG lineage without cloning the entire LOVE repository or creating a second runtime authority.

## Identity boundary
- LOVE: AI-system architecture/product core.
- PARADISE: software foundation, canonical runtime/governance environment.
- OG: governance/operating architecture; it is not copied as a second independent subsystem.

## Selection rule
KEEP only components with clear semantic ownership, useful capability, and evidence-backed value.
DISTILL documentation/contracts where the source repository contains useful design but full implementation would duplicate PARADISE responsibilities.
ARCHIVE or DROP legacy 99-command surfaces, binaries/installers, production deployment configuration, superseded branches, and duplicate frameworks.

## Canonical contracts carried forward
TaskContract → Submission → GovernanceSpec → GovernedExecutionPlan → DurableExecution.
AEGR remains the authorization/assurance boundary. Evidence and replay remain observational/provenance boundaries.

## Evidence boundary
Source snapshot is pinned to LOVE commit `41db094dcad8a857bf6dfc255e37ec889dd2515f` from branch `love-reconstruction-impl-20261003`. Per-artifact SHA-256 values are recorded in the migration manifest.

## Runtime boundary
The files under `projects/LOVE` are a distilled source/design snapshot. They are not automatically imported into `PARADISE/runtime` and do not bypass PARADISE semantic freeze V1.

## Migration completion criterion
Migration is complete when the selected snapshot is committed, integrity-checked, and independently attributable to the source commit. GitHub account ownership transfer is a separate identity/administrative operation and is not inferred from this content migration.
